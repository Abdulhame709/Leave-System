# إعداد اختبار Neon للتطوير بأمان

## قبل البدء
قاعدة Neon التي ذكرها صاحب المشروع مخصصة للتطوير وفارغة. نجح اختبار الاتصال وأُنشئ المخطط الأولي على قاعدة التطوير. نجح اختبار العزل الجزئي بعد تصحيح صلاحية دور الاختبار؛ بيانات الاختبار مؤقتة. لا تستخدم هذه الخطوات لقاعدة تشغيل حقيقية أو قاعدة تحتوي بيانات مهمة. لا تنشر رابط الاتصال أو كلمة المرور في المحادثة أو المستودع أو صورة شاشة.

أُعدّ ملف التشغيل اليدوي `.github/workflows/neon-development.yml`. يبدأ افتراضياً باختبار الاتصال فقط؛ لا يعدّل قاعدة البيانات في وضع `check`. الوضع الثاني `migrate_and_test` ينشئ مخطط `leave_app` وجداوله، ثم يشغّل اختبار العزل الجزئي ببيانات وهمية تُلغى بعد الاختبار. لا يحذف المخطط بعد نجاح الاختبار. إذا وُجد المخطط مسبقاً، يتوقف دون تعديله. إذا نجح إنشاؤه وفشل الاختبار، يبقى المخطط ويحتاج المراجعة قبل إعادة المحاولة. فشل بعض أنواع الصلاحيات في Neon قد يمنع الاختبار؛ لا تتجاوز ضوابط الأمان لإجباره على النجاح.

## اختبار الاتصال من فرع العمل قبل الدمج

أُضيف إجراء مستقل باسم `Neon development connection check` يعمل عند رفع تغيير في ملفه إلى فرع العمل الحالي فقط. يقرأ السر المحفوظ ويتحقق من الاتصال بعبارة `SELECT 1`، دون إنشاء جداول أو تشغيل ملفات الهجرة. لعرض النتيجة افتح تبويب Actions ثم اختر اسم الإجراء؛ لا يكشف النجاح هوية المشروع ولا يثبت صلاحيات العزل، ويجب التأكد بنفسك أن السر لقاعدة التطوير. لا يمنح هذا الإجراء الموافقة على أي تغيير للقاعدة.

## تهيئة قاعدة التطوير دون دمج

بموافقة صاحب المشروع على تهيئة قاعدة التطوير الفارغة، أُعدّ إجراء مستقل `Initialize Neon development schema` يعمل على فرع العمل عند رفع تغيير في ملفه فقط. يتحقق قبل التهيئة من عدم وجود مخطط `leave_app`، ويختبر إمكانية إنشاء دور مؤقت؛ ثم ينشئ الجداول ويختبر العزل جزئياً ببيانات وهمية تُلغى بعد الاختبار. عند فشل الاختبار بعد إنشاء الجداول تبقى الجداول، ولا تُعاد المحاولة دون مراجعة. لا يثبت الإجراء سلامة الدخول أو صلاحيات الأفراد.

## إتاحة ملف إنشاء المخطط وتشغيله

1. لكي يظهر التشغيل اليدوي في GitHub Actions، يجب أن يكون ملف الإجراء موجوداً على **الفرع الافتراضي** للمستودع. يجب مراجعة التغييرات على فرع العمل ودمجها بموافقة صاحب المشروع قبل ظهور الإجراء؛ لا تدمج دون مراجعة. بعدها يمكن اختيار فرع الجلسة الموثوق في شاشة التشغيل. لا تشغّل إجراءً من فرع غير موثوق يستطيع قراءة السر.
2. في لوحة Neon، افتح مشروع **التطوير** وفرع التطوير، ثم صفحة **Connect**. اختر اتصال PostgreSQL بمستخدم مخصص للإعداد وله صلاحيات تكفي للاختبار (ومنها إنشاء دور اختبار مؤقت). انسخ رابط الاتصال الآمن كما تعرضه Neon. رابط الاتصال يحتوي كلمة مرور؛ لا تشاركه معنا. يجب أن يكون لنطاق `neon.tech` وأن يتضمن `sslmode=require` أو `sslmode=verify-full`. يُفضّل اتصال مباشر لهذا الاختبار وليس اتصال تجميع، وتحقق من أنه يشير لقاعدة التطوير الفارغة.
3. في GitHub افتح المستودع، ثم **Settings → Secrets and variables → Actions → New repository secret**. اكتب اسم السر `NEON_DEV_DATABASE_URL`، وضع رابط الاتصال في خانة القيمة هناك فقط، ثم احفظه. لا تضع السر في ملف أو رسالة أو متغير ظاهر للواجهة. هذا السر ذو صلاحيات إعداد؛ لا تستخدمه لتشغيل التطبيق الفعلي.
4. بعد إتاحة الإجراء على GitHub، افتح **Actions → Neon development database (manual) → Run workflow**، واختر فرع العمل المراجع، ثم العملية `check`. شغّلها وراجع النتيجة: نجاح هذه الخطوة يعني الاتصال فقط، وليس إنشاء الجداول.
5. بعد التأكد من أن الاتصال يشير إلى قاعدة التطوير الفارغة، وبموافقة صريحة على إنشاء الجداول، شغّل الإجراء ثانية، واختر `migrate_and_test` واكتب `DEV_ONLY` في خانة التأكيد. راجع نتيجة كل خطوة. لا تعِد التشغيل عند الفشل أو وجود المخطط قبل مراجعة السبب.
6. عند الانتهاء غيّر أو احذف سر الإعداد إذا لم تعد تحتاجه، واحتفظ بمستخدم التطبيق محدود الصلاحيات منفصلاً عنه عند بنائه لاحقاً. لو انكشف رابط الاتصال، غيّر كلمة المرور في Neon وأبدل السر.

هذه الاختبارات لا تثبت صلاحيات الموظفين أو تسجيل الدخول أو سلامة التشغيل على الإنتاج. لا توجد بعد طريقة آمنة لاستخدام بيانات حقيقية.
